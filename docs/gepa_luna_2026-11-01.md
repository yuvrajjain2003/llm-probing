# GEPA prompt optimisation of the zero-shot Luna prompt (2026-11-01)

Round 5, ask 4: can automatic prompt optimisation (GEPA, via DSPy) improve the in-context baseline?

**Short answer: no.** Three tries, about $60 in total. With a score that rewards getting values right,
GEPA made the prompt worse on test. With ranking-only scores, it barely moved validation, and what it
found traded entropy ranking for remaining-length ranking. The original zero-shot prompt (k = 0) is
still the best in-context prompt we have.

## Setup (same for all three tries)

- **Prompt optimised:** the zero-shot GPT-6 Luna prompt from `src/baselines/icl_openai.py` (k = 0,
  the best in-context config: calibrated entropy R2 0.294 vs our probe's 0.309 on the same rows).
  Two versions, as before: `ckpt` (the item shows the checkpoint depth) and `blind` (depth hidden).
- **Models:** `gpt-6-luna`, reasoning effort high, for both the task and the reflection (prompt
  rewriting) step.
- **Data:** the 1-chain-per-question ICL rows (1,178 rows, 0-90% cuts). For each outer fold f, GEPA
  sees only the other folds' questions (~940 rows), split by question 70/30 into GEPA train
  (~656 rows, 111 questions) and GEPA validation (~282 rows, 47 questions). The test rows are fold f's
  rows, the same rows the earlier Luna runs and the probe were scored on.
- **Scoring on test:** the existing ICL scorer (`icl_predict.cmd_score`): raw R2 and calibrated R2
  (a per-cut linear map fitted on the other folds), committed accuracy. "Seed" below means the
  original prompt, rerun through DSPy; it reproduces the old Luna k = 0 run (entropy 0.296 vs 0.294).
- **Tools:** DSPy 3.4.1, GEPA 0.1.4 (`envs/dspy`). Code `src/baselines/gepa_luna.py`, launcher
  `runs/gepa/run_luna.sh`, monitor `src/baselines/gepa_monitor.py`.
- **Early-stop rule (tries 2 and 3), fixed before seeing data:** stop all runs if, in 2 or more
  folds, a candidate prompt beats the seed on GEPA validation but its within-cut rank correlation on
  entropy or remaining length drops by more than 0.05.

## Try 1: score = per-row squared error on the raw values

Per row and target, score `1 - err^2 / var` (var = that target's variance at that cut in GEPA train),
so its mean over a cut is R2. Feedback told the model each error and the typical range at that cut.
`auto="light"` (~1,500 metric calls per run), all 10 runs completed. Cost $28.3.

Validation improved in all 10 runs (e.g. 0.52 -> 0.60), but **test got worse on every target**.

Mean over 10-90% cuts, calibrated R2 (committed: accuracy), seed -> GEPA:

| version | entropy | p_mode | rem_len_mean | rem_len_std | committed |
|---|---|---|---|---|---|
| ckpt | 0.296 -> 0.139 | 0.228 -> 0.110 | 0.411 -> 0.105 | 0.128 -> 0.001 | 0.738 -> 0.672 |
| blind | 0.273 -> 0.124 | 0.220 -> 0.113 | 0.353 -> -0.060 | 0.084 -> 0.022 | |

Within-cut correlation also fell (ckpt entropy 0.55 -> 0.42, rem_len_mean 0.65 -> 0.44), while raw
(uncalibrated) remaining-length R2 improved (ckpt -0.14 -> +0.13).

**Why:** the optimised prompts (430-735 words vs the seed's 196) pasted in the training median and
10-90% range of each target at each cut. Predictions got the scale right but lost the ordering
between items. The published comparison is calibrated, so the scale gain is worth nothing there and
only the ranking loss shows. This is the same mechanism as round 6's finding that in-context
examples hurt (they supply scale and break ranking).

## Try 2: the model predicts within-cut percentiles (`--pct`)

The model outputs each target as a percentile 0-100 relative to other items at the same cut; score
`1 - (p - t)^2 / var` on percentiles; feedback says only "ranked too high / too low", never typical
values. At test, percentiles are mapped back to values with the GEPA-train quantiles at that cut.

**Stopped after ~25 minutes by the rule** (~$7 est.): ckpt fold 2 validation 0.649 -> 0.671 with entropy
rank corr 0.645 -> 0.578 and rem_len_mean 0.671 -> 0.599; ckpt fold 3 0.618 -> 0.622 with entropy
0.584 -> 0.489. 15 of the other 17 new prompts scored below the seed.

**Why:** squared error on percentiles still rewards pulling predictions toward 50 when the ranking is
only moderately good (the winning fold-2 prompt shrank its entropy prediction spread from 31 to 24
percentile points). So it was still not a ranking-only score.

## Try 3: whole-batch rank score (`--rank`)

Same percentile outputs, but GEPA scores each batch as a whole: mean over the four regression targets
of Spearman(predicted percentile, true percentile), mapped to (rho + 1) / 2, given to every row of
the batch (DSPy's GEPA adapter `evaluate` is patched; the per-row metric still supplies feedback text).
Invariant to any monotone rescaling, so neither scale nor shrinkage can earn score. Committed not
scored. Minibatch 30 rows (default 3), 2,500 metric calls per run.

**Stopped by the rule** (~$25 est.), after 7 of 10 runs had used their budget:

| run | val score, seed -> best | entropy rank corr | rem_len_mean rank corr |
|---|---|---|---|
| ckpt fold 3 | 0.727 -> 0.731 | 0.569 -> 0.476 | 0.617 -> 0.655 |
| blind fold 4 | 0.723 -> 0.729 | 0.583 -> 0.516 | 0.533 -> 0.516 |

- **Validation barely moved:** in the 7 finished runs the best prompt beat the seed by 0.000-0.008
  on the (rho + 1) / 2 scale (at most ~0.016 in rho), and 4 of 7 kept the seed.
- **Consistent trade-off:** new prompts tended to rank remaining length better and entropy worse.
- **Partial test** (the two folds where a new prompt had been chosen and tested, within-cut Spearman,
  seed -> GEPA): ckpt fold 1 entropy 0.48 -> 0.41, rem_len_mean 0.50 -> 0.57; blind fold 2 entropy
  0.60 -> 0.62, rem_len_mean 0.59 -> 0.65. Not a full 5-fold result.

## Conclusions

1. A per-row error score teaches GEPA the output scale, which a calibrated comparison does not
   reward, at the cost of ranking. Any future run must use a scale-free, ranking-only score.
2. With a ranking-only score, GEPA finds no prompt that ranks better overall; gains on one target
   come at the expense of another.
3. Consistent with round 6: the frontier model's zero-shot entropy tie with our probe is mostly
   question difficulty, which an instruction rewrite does not add to.

## Gemma-4-31B, whole dataset (2026-11-03 to 11-04)

Local Gemma-4-31B-it (thinking off, vLLM on 2 H100) as task and reflection model, so no API cost.
All 25 chains per question (~24,800 rows; per fold ~14,000 GEPA-train and ~5,900 val rows), try-3
rank metric, minibatch 30, budget 45,000 metric calls per run. Early-stop rule as above.

**Setup search on fold 0 (`ckpt`):**
- Minibatch 150: stopped by the rule (val 0.660 -> 0.665, but rem_len_mean rank corr 0.323 -> 0.178).
- Minibatch 30: every target improved on val (0.660 -> 0.758). Chosen.
- Three plumbing fixes were needed first: the reflection prompt overflowed Gemma's 32k context
  (now at most 10 examples, each cut to its start and end); litellm's lazy import races under many
  threads (now imported up front); a DSPy cache shared on NFS by jobs on two nodes was corrupted
  (now one cache per job).

**Full run, 5 folds x 2 versions** (rule never fired; 9 of 10 runs had every new prompt beat the
seed on val). Mean over 10-90%, calibrated R2 and within-cut Spearman, 95% paired question
bootstrap:

| version | target | seed R2 | GEPA R2 | probe R2 | seed rho | GEPA rho | probe rho |
|---|---|---|---|---|---|---|---|
| ckpt | entropy | 0.138 | 0.232 | 0.289 | 0.346 | 0.495 | 0.542 |
| ckpt | p_mode | 0.092 | 0.192 | 0.251 | 0.338 | 0.488 | 0.534 |
| ckpt | rem_len_mean | 0.027 | 0.085 | 0.524 | 0.170 | 0.403 | 0.771 |
| ckpt | rem_len_std | 0.000 | -0.027 | 0.298 | -0.055 | 0.164 | 0.576 |
| blind | entropy | 0.146 | 0.244 | 0.289 | 0.384 | 0.504 | 0.542 |
| blind | p_mode | 0.146 | 0.187 | 0.251 | 0.446 | 0.493 | 0.534 |
| blind | rem_len_mean | 0.027 | 0.173 | 0.524 | 0.257 | 0.511 | 0.771 |
| blind | rem_len_std | -0.013 | -0.005 | 0.298 | 0.013 | 0.226 | 0.576 |

- **GEPA beats its seed** on every target and statistic except rem_len_std R2.
- **GEPA stays significantly below the probe** on all four targets in both versions (entropy R2
  -0.056 [-0.103, -0.012] ckpt, -0.045 [-0.092, -0.005] blind).
- **But the seed here is a weak baseline.** It is the percentile-output prompt, which scores well
  below Gemma's original value-output zero-shot prompt from R1. On the 980 rows both cover (calibrated
  R2, entropy / remaining length): original zero-shot 0.262 / 0.283, percentile seed 0.139 / -0.008,
  GEPA ckpt 0.263 / 0.086, GEPA blind 0.251 / 0.177. So GEPA wins back what the percentile format lost:
  it ties plain zero-shot on entropy and p_mode and is still below it on both length targets.

**0% cut only, `blind`, try-1 metric** (198 rows, one per question): val roughly doubled in every
fold, but test calibrated R2 did not change (entropy 0.067 -> 0.072, n.s.; 0% probe 0.234). Entropy
ranking improved (Spearman 0.152 -> 0.349, sig.), length did not, and raw R2 rose a lot (scale
learning, as in try 1).

**Conclusion so far:** with a ranking-only score and enough data GEPA does find better prompts than
its own seed, but none better than the plain zero-shot value prompt, and none close to the probe on
remaining length.
